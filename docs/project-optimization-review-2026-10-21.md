# 项目检验与优化建议（2026-10-21）

状态：本次实查形成的优化建议，供后续实施拆分使用。本文不替代已批准规格和任务清单，不表示下述功能已经实现或正式数据库入口已经切换。

## 1. 结论与优化目标

项目方向成立：以可复核的跨行业资料，帮助用户选出愿意投入两周验证的 1–3 个副业方向。当前资料、证据、去重、恢复和私人隔离已有基础，下一阶段最有价值的工作是补齐“看懂资料 → 比较方向 → 明确下一步”的使用闭环。

建议保留现有单机、Python 标准库、SQLite 和原生网页架构。当前没有证据表明需要更换框架、拆服务、引入向量数据库或增加第二套调度器。先完成少量能直接减少阅读与选择成本的切片，再处理正式入口切换。

初次评审仅完善文档和纠正文档中的现状描述；随后按用户要求补充 OPT-13，并整理历史研究资料的中文表述。应用代码、研究结论、用户选择和每日调度未改动。

## 4. 具体建议与验收标准

### OPT-01：修正点子统计和状态筛选

现状依据：[首页](../src/local_web/static/index.html)把全部点子数量标为“待验证点子”；状态选项固定为待验证、可读、受限。[索引](../ideas/INDEX.md)实际包含 3 条候选和 1 条搁置，因此用户无法直接筛出当前最值得比较的方向。

具体修改：

- 将总数标签改为“点子总数”，另显示待验证、候选、搁置的实际数量；“精选”独立展示，当前为 0。
- 点子状态选项从点子研究状态生成；来源切换为访问状态筛选。筛选名称明确区分“研究状态”和“访问状态”。
- 点子状态采用明确值匹配，避免继续依赖自然语言 `includes()`。来源的“首页可读、讨论未读”等混合说明保留为备注，不直接当成访问成功。
- 给 E3 加简短说明：“存在采购/报价/付款信号，具体类型看证据”；不能把 E3 一律显示成已付款。

主要位置：`static/index.html`、`static/app.js`、`catalog.py` 和对应测试。

验收：真实资料得到总数 20、待验证 16、候选 3、搁置 1；选择候选只显示 `011/012/013`，选择搁置只显示 `004`。E3 仍显示 5 条，并保留历史采购、当前意向和付款未知的区别。加入新的合法状态后，筛选不能静默遗漏。

### OPT-02：区分来源入口、站点与独立样本

现状依据：[来源索引](../sources/INDEX.md)的 GL03、GL07、GL09、GL10、GL21 都属于 Reddit；[STATE](../research/STATE.md)却使用“30 站”，[目录统计](../src/local_web/catalog.py)直接按来源 ID 计数。条目应保留，但这些口径不能互换。

具体修改：

- 当前阶段先显示“来源入口 30 / 不同 hostname 26”，并在状态摘要中明确口径。hostname 仅是可复现的统计口径，不自动等于独立平台或独立买方。
- 后续需要按平台聚合时，为已有来源补明确的 `platformKey`，保留现有全部 ID 和板块定位；未经审阅不要靠截取域名尾部猜测平台归属。
- 在证据回顾中分别统计来源入口、平台、不同作者/企业和原始讨论。转载、同作者跨板块、同帖回复不能自动变成独立需求。

验收：来源记录仍为 30；Reddit 五个入口可以分别打开，但平台聚合只归一组。同站独立用户仍可支撑 E2，不因归组而丢失证据，也不被标成跨站 E2。

### OPT-03：修复编号证据的阅读结构

现状依据：[Markdown 渲染器](../src/local_web/markdown.py)只识别无序列表，不识别 `1.` 编号列表。实际打开 [n8n 方向](../ideas/IDEA-20261021-011.md)时，7 条证据、反证被合成一个长段落，难以核对哪条主张对应哪个来源。

具体修改：

- 支持安全的 `<ol><li>` 渲染，并正确处理段落、编号列表、无序列表和表格之间的切换。
- 增加行内代码显示，改善 ID、API 字段和技术名的辨识；保持现有 HTML 转义与链接协议限制。
- 给详情增加“证据 / 反证与替代 / 个人匹配 / 下一步 / 历史”页内定位；先复用已有小标题，不复制正文生成另一份结论。

验收：`011` 的编号部分渲染为 7 个独立有序列表项；原始链接数量与目标不变。混合列表、表格切换和恶意 HTML/链接均有回归，不能为显示效果放宽正文安全边界。

### OPT-04：增加方向比较与两周验证简报

现状依据：[能力划分](../CAPABILITY-MAP.md)中的 opportunity-review 尚无规格；[点子索引](../ideas/INDEX.md)有 3 条候选、精选为空。资料已能说明问题，但用户仍需自行从长文中提取成本、维护负担和验证顺序。

具体修改：

- 先为 `011/012/013` 做一份可并排阅读的研究比较简报；`018` 作为国内方向对照。前三条属于相近的自动化交付机会，应解释客户和交付边界的差异，不能当作三份完全独立的市场机会。
- 比较字段固定为：目标客户、最小可售交付、原始需求、付费信号类型、强替代、预计主动工时及假设、会议/响应要求、持续支出、可触达渠道、最大未知、下一步核验。
- 复用现有 Assessment 的匹配、理由、成本区间、未知项和证据引用。不同币种报价只保留原币种和性质；未知工时与成本保持未知，不生成未经确认的加权总分。
- 每份两周建议只验证一个关键假设，写出交付边界、投入上限草案、继续/停止条件；没有实际结果时不填成功或付费试单。
- 页面比较先支持最多 3 条、字段对齐和明确空值；不用雷达图表达没有可靠数值的判断。

建议先核验“固定价排障是否能在有限时段完成”，因为它相对完整实施更容易限定交付；其次检查“白标合作是否接受异步与有上限的支持”。这是研究优先级推断，尚非正式精选。n8n 完整实施仍需核对紧急响应和维护工时；国内广告工单仍需第二家独立企业样本及现成产品对比。

验收：用户能在同一张比较表中看到每个候选的关键差异、证据链接、最大风险和一个下一步；可保留精选为空，并说明差哪项证据。两周建议最多安排 28 小时可投入时间，实际计划应留出研究与返工空间，不把满额时间全部许诺给交付。

边界：本任务可以准备研究简报和实验设计；联系客户、申请岗位、发帖、购买服务或开发副业演示产品仍按现有授权边界处理，不能因文档写了实验计划就自动执行。

### OPT-05：改善默认首页与手机首屏

现状依据：[前端](../src/local_web/static/app.js)按目录顺序显示，首次进入先看到 30 个来源，点子排在趋势之后；[样式](../src/local_web/static/app.css)在手机上把统计和完整筛选纵向展开。实查 390 × 844 下列表区起点约为文档第 1242 像素。

具体修改：

- 默认进入“点子”页，提供“待比较候选 / 全部点子 / 趋势 / 来源”入口；候选可以作为快捷筛选，但不自动标为精选或准备验证。
- 首页压缩标题高度，统计采用紧凑一行或两行；手机保留搜索和筛选按钮，高级条件折叠并显示已选条件数。
- 默认按最近实质更新排序，支持切换更新时间、研究状态；相同日期以稳定 ID 排序，避免每次刷新跳动。
- 点子列表优先显示“谁的问题、可能交付什么、为何适合、最大未知”；ID 和长访问说明降为次要信息。没有提取到正文摘要时明确缺失，不临时编造。
- 详情使用稳定 URL 或 hash 定位；关闭后保留筛选与滚动位置，支持返回键。外部来源另页打开时同时保留安全链接属性。

建议布局：

```text
机会观察室   集中收集   数据更新时间 / 刷新
候选 3 | 点子 20 | 趋势 1 | 来源入口 30
搜索 __________________  筛选(2)  排序
候选比较入口：选择最多 3 个方向
方向标题｜人群与问题｜证据性质｜匹配｜最大未知
```

验收：390 × 844、页面顶部且筛选折叠时能看到至少第一条点子标题；320/768/1440 宽度无横向溢出。刷新可恢复所选条件，详情可直接定位；键盘可完成筛选、打开/关闭详情，焦点返回触发项。

### OPT-06：规范展示字段，补齐有用筛选

现状依据：[目录适配器](../src/local_web/catalog.py)把点子“个人匹配”放入 `summary`，证据和状态主要是整段文字；来源 `updatedAt` 恒为空。现有页面没有意图要求的副业类型、投入成本、个人匹配筛选，但 [records 查询](records-operations.md)已有这些概念。

分两步实施：

1. 先在展示契约中分开 `fit`、`researchStatus`、`evidenceLevel`、`evidenceNote`、`summary`；保留原说明和未知值。支付意向、供应报价、聘用/上线结果、付款确认应按具体证据展示，避免用一个条目级布尔值覆盖所有主张。
2. 在对应元数据已可靠可取后加入行业、市场、交付模式、匹配筛选；成本筛选必须带币种，并提供“成本未知”。时间筛选区分首次收录、原帖发布、实质更新和最近成功读取。

当前过渡期通过 Markdown 只读适配形成展示模型；正式切换后通过 records 查询形成同一展示契约。展示模型不保存为第二份可人工修改的研究数据库。不为每个页面单独解析一遍正文或硬编码点子 ID。

验收：“较适合”在当前资料中得到 4 条，“暂不适合”得到 2 条；相同条件在列表与比较页一致。未知成本不能满足“成本为零”或“已知低于预算”，历史采购不能因访问日期是今天而变成近期采购。旧详情和稳定 ID 继续可用。

### OPT-07：准备正式入口切换并接入私人操作

现状依据：[存储决策](decisions/001-local-records-storage.md)、[操作说明](records-operations.md)与当前 STATE 明确保留 Markdown 正式入口。[PersonalStore](../src/records/personal.py)已经实现版本校验、幂等操作与私人历史，但要求关联研究记录存在于库中。当前只给页面加按钮无法完成可靠接入。

建议使用现有切换路径，先做准备清单，再决定切换时点：

1. 用最新资料重建迁移预览；本轮 103 条记录是可复核基线，后续变化后需重新预览。
2. 在新库演练迁移、公开导出、重导、完整备份和恢复；抽查原文、日期精度、ID、证据关系和用户状态。
3. 设计短暂写入冻结与回退方案，复核演练期间新增资料，再取得现行操作说明要求的正式切换确认。
4. 切换后研究写入走 records，网页读取同一服务边界，公开 JSON 为确定性快照，Markdown 保留原文/阅读视图；同时更新手册和现有自动化入口。
5. 网页调用现有个人状态能力，支持收藏、忽略、准备验证及历史；使用 expectedRevision 和 operationId，冲突时读回并提示。

验收：两台允许访问的设备看到相同个人状态；重启、研究更新、合并和备份恢复后选择仍保留；研究入口无法覆盖个人选择，公开导出不含私人备注。加入写接口前补本机/局域网访问控制、Origin 校验与写请求保护，并验证跨站请求被拒绝。

正式切换是独立交付，不能和页面美化混在一次提交中。暂不切换时先完成只读比较与展示优化；本轮没有创建正式库，也没有把私人状态塞进浏览器临时存储。

### OPT-08：按缺口和证据增量安排研究

现状依据：[研究手册](agent/RESEARCH-WORKFLOW.md)已有“每轮一个问题和一个缺口、三轮无新证据则调整渠道”等规则，[覆盖模块](../src/research/coverage.py)也已实现对应校验。缺口在于正式研究的 Markdown 过程尚未接入结构化运行入口，不能把临时库能力视为自动任务已经使用。

具体修改：

- 保留现有有界预算，每轮明确一个覆盖缺口和一个候选的关键未知；二者允许使用同一来源，查询不足时宁可减少任务。
- 研究记录使用固定结果分类：新增需求、独立补证、采购进展、反证、无变化、读取失败。每项引用实际读取位置；新链接数不等于新需求数。
- 周回顾展示“行业/受众 × 国内外 × 服务/产品”等覆盖表，区分已读需求、仅有供给推广和未覆盖；重点补国内非技术买方样本。
- 来源健康同时保留读取方式、last_attempt、last_success 和失败原因。会话浏览成功与程序 Reader 受限分别记录，不互相覆盖成功状态。
- 跟踪每轮已读讨论数、真正改变判断的证据数、重复/受限数及实际用时；这些指标用于调整渠道，不成为新的硬性入库配额。

### OPT-09：增加资料一致性检查与页面回归

具体修改：
