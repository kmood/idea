# 研究执行手册

本文件落实 AGENTS.md 的研究流程；不是网站数据结构/API 规格。现阶段用 Markdown 记录，后续实现保留 ID 与历史。

2026-10-27用户授权转为[深度尽调任务](../intent/deep-opportunity-research.md)。以下基础准入、来源分级、恢复和历史规则继续生效；当前优先执行第9节，不以扩库数量推进阶段。

## 1. 恢复现场与设定范围

- 读取 STATE、Git 状态、相关索引。确认 origin、分支及上轮待推送提交；先判断是否能安全重试，勿重复生成上轮结果。
- 人工研究与现有每日自动化均执行 [中文书写约定](../../AGENTS.md#中文书写约定)：收集内容、记录和提交说明使用中文；专有名词及必须精确保留的技术定位信息按该约定处理。
- 每轮选一个主要方向和一个能改变判断的未知项，先说明预期推翻或支持什么；可保留少量跨行业对照，但研究对象不等于候选或精选。
- 默认单轮最多12组查询、深入读取10个具体案例，另对辅助核验读取设有限预算；均为上限。原200条仅为历史覆盖参照，不按数量推进当前尽调。
- 开始写入前重新检查涉及文件；发现被他人编辑，不覆盖。人工任务与定时轮次发生重叠时由后进入者跳过写入并保留待办，不能仅依赖状态文字充当可靠锁。

## 2. 来源与覆盖

- 来源至少记录稳定 ID、主域名、具体入口、语言/受众、行业、访问日期和状态。仅入口可读不等于具体讨论可读。
- 个人匹配按整个 IT 能力范围评估，包括开发、测试、数据、云与运维、集成、产品/项目、设计协作、技术支持和其他可迁移能力；不再把后端开发作为默认边界。具体能力未知时记录未知，不自行补齐。
- 新站先建档，再读取具体讨论。可用公开页面、站点提供的订阅和搜索定位；受限页面标记原因并换可访问来源。
- 记录原帖日期与本次访问日期，无法确认日期就写未知。优先近期需求，但经典案例可入库并标为历史案例，不能当作当前需求。
- 集中收集维护覆盖回顾：行业/人群、国内/海外、服务/产品模式、已读来源、有效发现和缺口。AI 应用重点关注真实工作变化，不仅看工具发布；但信息化、AI 或开发不是调研入口的必要条件。
- 调研方向可覆盖任何可能适合个人副业的行业和模式，包括服务、产品、内容、培训及行业服务。个人匹配用于解释优先级和精选，不用于排除仍满足严格准入条件的方向。
- 建议轮换：内容与营销、教育与培训、电商与零售、专业服务、小企业运营、开发者工具，以及其他尚未覆盖但可能适合个人副业的方向。此列表是探索起点，不是白名单，也不是必须凑齐的类目。
- 区分真实用户讨论、供给方推广、成功案例与研究报告；同一新闻的转载不算独立证据。非交流网站可作为具体结论的辅助核验来源。
- 多文档来源编号约定：同一买方、同一项目在不同交易环节产生的采购文件、澄清、成交公告、合同与验收等文档，共用一个来源 ID，Source 主 URL 取最早或主文档，其余文档 URL 在来源索引、点子正文与证据摘要中显式登记并标注环节；证据 claim 必须分环节描述，不得把预算、授标、结算沿链自动推定。只有出现不同买方、不同项目或可独立成立的新交易时才分配新 ID。典型先例：CN313（采购文件 52607.htm + 成交公告 66912.htm 共用一个 Source）。

## 3. 分类和证据

| 内容 | 最低收录条件 | 缺少条件时 |
| --- | --- | --- |
| 来源 | 可追溯入口、受众、实际访问状态 | 记录为待核验来源，不声称可挖掘 |
| 趋势/灵感 | 已读具体来源、变化是什么、为何可能重要 | 摘要/打不开页面只进入运行记录待办 |
| 副业点子 | 已读原帖/案例、服务对象、具体问题、可能的赚钱方式 | 需求或商业路径尚不明确则放趋势，不补写虚构事实 |

计入累计有效点子数还必须记录证据等级、反证或替代、未知项、个人匹配和历史。这里的“有效”只表示记录满足可复核准入条件；E1/E2 点子仍可能在后续被搁置或淘汰，不能写成已验证市场需求。

赚钱方式可以是研究助手推断，但必须标为假设。标题“AI 赋能某行业”不足以成为点子；应说明谁在什么情境下为何可能买单。

证据按具体主张记录，不能给一个链接贴上标签就推断全部结论成立：
- E0：已读资料支持的趋势/推测，没有直接需求证据。
- E1：原始具体需求或案例，但没有独立复核。
- E2：独立用户/来源重复出现同类问题；区分同站不同用户和跨站证据。
- E3：可核验的采购、付费试单或成交信号；明确是“意向”“报价/采购”还是“已付款”，不要混同。

作者自述收入和推广材料单独标记，不直接升级为已验证成交。新反证与旧证据并存，解释冲突；网页删除只是可访问性下降，不自动证明原结论错误。

## 4. 去重与历史

- 先用原始 URL/帖子 ID 查重，再按“人群＋痛点＋交付结果”判断语义重复。去掉明确的跟踪参数时保留原始 URL，不删影响页面内容的查询参数。
- 同一问题的不同商业模式/目标客户可保留为变体并互相链接；只有重复明确时合并，不确定先标记“可能重复”。
- 新条目使用稳定 ID，例如 IDEA-20261014-001、TREND-20261014-001；写入前查重，不按标题变化重命名 ID。现有来源 ID 保持不变。
- 条目内维护历史表：日期时间（Asia/Shanghai）、事件、前后变化、原因、证据链接、执行者。首次收录、补证、更正、状态变化、失效、合并均记录。
- 合并保留旧条目与 merged_into 关联及原始证据；趋势转点子保留 derived_from 关联。不把删除旧记录当作去重。
- 不用新分析重写用户操作；人工选择和研究状态分开。用户未给实验反馈时不得标为验证成功。

## 5. 适配与精选

广泛收录后，再判断个人匹配：较适合/有条件适合/暂不适合/未知，并解释时间、资金、获客、交付维护、沟通和技能各维度的依据。不生成貌似精确的收益概率；未核验成本写未知，估算写范围与假设。

精选最多 1–3 个，宁缺勿滥；没有足够证据可为空。精选至少要回答：
1. 真实目标人群和问题由哪条具体证据支撑？有哪些反证或免费替代？
2. 为什么适合用户，最大不确定性是什么，如何找到可触达客户？
3. 建议用多长探索周期、分几个阶段验证付费意向/试单，什么结果支持继续、延长或搁置？

入库不要求完整商业计划。精选才深入补充竞品、工时、持续成本、建议探索周期和分阶段验证步骤，避免收集阶段的过高门槛。默认可先按 4–6 周规划；简单方向可缩短，复杂交付或较长获客周期可延长至 6–12 周或更久，但必须写明阶段性退出条件，不能无限投入。

## 6. 阶段与失败处理

- 当前阶段：深度尽调（用户于2026-10-27授权），既有集中收集记录保持历史原貌。按研究对象的假设、证据缺口和下一轮核验问题恢复；不把阶段变更当作历史收集已验收。
- 增量阶段优先按来源上次成功采样的位置/时间续读，保留少量重叠以发现旧帖新回复。访问失败不推进该来源游标；记录失败与下次重试条件。
- 每次更新来源须区分 last_attempt 与 last_success；不要用失败日期冒充核验完成时间。
- 临时网络错误本轮最多重试一次；登录、权限和限流问题不密集重试。连续同类失败则降低该来源频率，保留错误摘要与替代入口。
- 连续三轮没有实质新增证据时调整查询/渠道，而非降低入库标准；已经处于增量阶段时允许低频维护。

## 7. 验收、提交与报告

- 检查：来源支撑结论，事实/推断/未知可区分，ID 唯一，索引链接可达，重复处理有理由，旧历史与用户记录保留，没有凭据或无关个人信息。
- 对本轮修改全部执行以上检查。缺少条件的内容留待办，不伪装为通过核验。
- 检查标题、链接显示文字、摘要、分析及历史说明是否使用中文；外文标题译述不得改变原意，原始 URL、ID、查询和凭据不得改写。历史资料修正后同步核对迁移映射与原文摘要。
- 每轮在 research/runs/<实际日期时间>-<主题>.md 记录研究问题、范围/渠道、读取成功/失败、独立案例与去重、研究对象/候选/新增数、证据变化、已减少的不确定性、反证、剩余缺口与断点。零新增也记简短记录；相同runId重试更新同轮，不重复生成。使用实际Asia/Shanghai时间，不预写未来轮次。
- Git 同步前核验 origin，fetch 后检查 ahead/behind；仅在干净工作区 fast-forward。分叉、非本任务提交或冲突时停止推送并报告，研究可保留本地成果。
- 只暂存本轮路径，检查暂存差异后提交。push 后查询远程分支；若远程已前进，fetch 并确认本轮提交为其祖先才算成功，不强推。
- 提交标题、正文和类型前缀使用中文，例如 `文档：补充自动化采购证据`；提交前检查拟用说明，不沿用英文提交模板。
- 推送失败保留同一提交，下轮重试；同步状态可由 Git 推导，不为了写入“已推送”再产生一个永远追赶的状态提交。
- 报告以新增/更新/合并、证据变化、精选及阻碍为主。仅初始化规则或试演时明确标注，不能虚报已完成真实采集。

## 8. 点子记录最小模板

```markdown
# <稳定 ID> <具体方向>
- 首次收录 / 最近实质更新：
- 类型 / 行业 / 市场：
- 研究状态：待验证（与用户收藏等操作分开）
- 服务对象与问题：
- 可能的赚钱方式：<事实或假设>
- 来源：<来源 ID、具体 URL、发布时间/未知、访问时间>
- 证据：<支撑哪项主张、等级、作者声称/事实/推断、反证>
- 个人匹配：<等级、理由、未知项>
- 下步核验：<一个最关键问题>
- 关联：<变体/derived_from/merged_into，无则省略>

| 时间 | 事件与变化 | 原因/证据 | 执行者 |
| --- | --- | --- | --- |
```

趋势记录保留 ID、具体变化、原始来源、可能影响（标记推断）、待验证问题和历史即可，不强行填商业模式。

## 9. 深度尽调当前执行协议

长期审查与候选守门按[质量监控协议](QUALITY-MONITOR.md)执行；当前审查基线见[2026-11-04质量复核](../../research/deep/2026-11-04-library-quality-review.md)。

- 每个方向拆为需求、付款决策者、现有替代、获客、选择新人理由、交付、验收、付款、售后与复购假设；优先查最可能推翻方向的一项，不要求凑齐所有环节才能记基础资料。
- 原始材料优先于整理稿：买方帖子及回复、需求书、澄清、合同、具体订单、样件、修改、验收、结算、退款/失败记录。识别发帖人是买方、供应商、开发者调研者还是转述者；不得把讨论热度或开发者方案当买方需求。
- 逐项记录原始定位、日期、已读位置、角色、信号类型、支持主张、不能支持的结论、独立性、反证和未知。同一事件的采购公告/合同/结果不重复计独立样本；同平台不同订单仅是不同订单，买方匿名时独立买方数未知。
- 交易链分环节记录：合同额、成交候选、平台已结算、法院应付款、银行实际回款和净利润分别呈现；不能沿链自动推定。保持E0–E3旧口径，额外说明实际商业信号。
- 完整投入包括获客、沟通、制作、修改、通勤、售后、设备/许可、税费/平台费、资金占用；未知保留未知。情景计算不冒充实测，不因数字精确而声称真实时薪。
- 公开尽调记录放 research/deep/，只放可公开的市场证据、反证和一般结论；私人获客路径、适配、探索周期及反馈放已忽略的 .local/research/deep/，不写入公开记录、Git或公开导出。旧条目既存私人段落暂不批量迁移，禁止扩大暴露。
- 私人验证方案应写输入/输出、样件与验收、工时/预算上限、阶段目标和继续/延长/暂停条件。模拟样件只能证明技术交付；访谈/客户触达/发帖/收款/购买/投放/副业产品开发仍须对应授权，当前先完成桌面研究和方案。
- 第三方应能按证据编号和定位复核结论；预先写明什么新证据会推翻结论。自动测试只验证结构和一致性，不能证明市场成功。缺获客、周期或交付边界不得进入候选/精选。
- 连续重复机构整包、同平台需求大厅或供应商报价却不减少未知时，换证据类型；全范围作为发现边界，不固定少数网站，也不为覆盖而扩大条目。
